More Outcomes per Dollar

“Optimizing agentic work means more accepted outcomes for each dollar spent. Fewer tokens is sometimes the route there, and sometimes the way to miss it.”

With spend attributed and signals owned, the next step is to change things. The order you change them in, and how you check each change, decides whether yield goes up or only the bill goes down.

The wrong scoreboard

The easiest number to improve is token count. Shorter prompts, a smaller model, a lower cap on retries: each reduces spend immediately and shows up on the next report. None of them says anything about whether the work still gets done. The Reframe page gave the failure case: a model 40% cheaper per token that converts at half the rate leaves you paying more per accepted outcome than before.

The scoreboard for this stage is accepted outcomes per dollar, per task class, before and after a change. In the terms used across this hub, that is AES set against spend. If a change lowers spend and AES holds, it is a saving. If it lowers spend and AES falls further, it is a loss that happens to look good on the invoice.

A ladder of levers

The levers available are familiar engineering practice. What is less familiar is ordering them by effect on yield rather than by ease. The order below is my proposal, reasoned from the earlier pages rather than measured across workloads.

  1. Stop work that does not convert. The cheapest token is the one spent on a task class you decided not to run. If a class sits below its yield floor and the Manage signals call it a yield event, pausing it beats tuning it.
  2. Fix the loop. Stop rules, context hygiene, cleaner tool outputs and sub-agents that return summaries rather than transcripts. This changes how many iterations a task needs and how much each one carries. One published result found a 41% cost reduction from harness changes alone, with no change of model.
  3. Cache the stable prefix. Keep system instructions and tool definitions fixed in order and content so that repeated input is billed at the cached rate. This lowers price without touching what the model sees.
  4. Route by task class. Send each class to the cheapest model tier that holds its yield, using the Value of a Token test to decide when an upgrade is worth it.
  5. Batch what can wait. Work that does not need an answer in seconds can often run asynchronously at a lower rate.
  6. Set quotas and negotiate rates. Useful, and the furthest from yield. These change what each token costs and nothing about what it produces.

The top of the ladder acts on yield risk. The bottom acts on price risk. Teams under cost pressure tend to start at the bottom because those levers need no change to the work. That is why they so often produce a smaller bill and an unchanged yield.

One lever, one class, one comparison

Each change should be small enough that its effect can be read. Pick one task class, pull one lever, and compare yield per dollar for that class over a period long enough to cover its normal variation. Changing three things at once across all classes produces a number nobody can explain, and the Review stage will have nothing to decide with.

The first 30 days

For a team starting from an invoice and nothing else, a month is enough to complete one turn of the loop on a small scale.

  • Week 1. Add attribution tags to every call. Pick two or three task classes and write a baseline card for each.
  • Week 2. Read the token mix and the accept/reject record per class. Find the class with the lowest yield per dollar.
  • Week 3. Apply one lever to that class, starting as high on the ladder as you can.
  • Week 4. Compare yield per dollar against the baseline card and write the result down, whichever way it went. That record is the input to Review.
DO NOT OPTIMIZE THE WEAKEST LINK AWAY

The Instruments page described quality as an O-ring: adoption tips on the worst-covered piece of work, not the average. A saving that thins out review or test effort on the one story that was already weakest can lower spend and collapse adoption at the same time. Cut gold-plating, where the quality curve has flattened, and protect spend in the leverage zone, where it is steep.

GO DEEPER: why the order puts price levers last

A price lever scales every token by the same factor, so its best case is a proportional saving on spend that was already converting at whatever rate it converted at. A yield lever changes the conversion rate itself: fewer iterations rejected, fewer tasks handed back to a human, less output that ships and goes unused. Because AES is a product of three ratios, a modest improvement in the weakest ratio can move it more than a large discount moves spend. That argument is arithmetic about the structure of the measure. Specified, not yet measured: how large the effect is for a given task class is an empirical question.
