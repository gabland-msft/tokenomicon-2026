THE AGENTIC LOOP

The Agentic Loop

“The loop is the cost multiplier. Most token spend is invisible — like an iceberg.”

A single model call already carries five priced token classes. An agentic task doesn’t make one call and stop: it cycles Read → Generate → Execute → Evaluate, and repeats until the work passes or a limit is hit. That repetition multiplies cost rather than adding it, and most of the multiplication never reaches the screen.

Cost multiplies. It doesn’t add.

The loop itself is simple: read the current state, generate a step, execute it, evaluate the result, and go again if the work isn’t done. Each pass around that cycle is a full model call with its own five-part cost structure: input, reasoning, output, cache-write, cache-read.

THE MULTIPLIER

cost ≈ per-call cost × ℓ (iterations) × f (fan-out)

A one-dollar call looped 10 times is $10; add 3-way fan-out (parallel sub-agents) and the same work item becomes $30. That compounds across every item in a backlog.

01

The mechanics

Agentic systems cycle Read → Generate → Execute → Evaluate → repeat, until the work passes or a limit is hit. Every iteration is a full call, not a cheap increment.

02

The safety valve

A halt-and-escalate mechanism (a monotonic cost detector) stops the loop and escalates to a human before the next iteration would exceed the remaining budget, rather than looping blind.

03

Two-layer policy

Allocation policy (triage: which tier, which model, how many loops) is separate from execution policy (doing the work). A cheap token spent on triage prevents expensive tokens spent on rework.

Why looping multiplies cost

The multiplier tracks a real asymmetry between prefill and decode in how the accelerator does the work, which is what makes output price around 5× input and a cache read price so far below a fresh input token (see the prefill/decode mechanics and Foundry's cache-pricing regimes on the Tokens page). What that page doesn’t cover is what this asymmetry does specifically inside a loop. The part that actually bites is the KV cache: during prefill, each layer computes a key/value vector per token so later tokens can attend to earlier ones without recomputing them. That tensor has to be read every decode step, by every token in context, with no sharing across sequences. That’s why continuous batching amortizes the model’s weights but not this. And because most agent harnesses re-send the entire conversation history on every turn rather than diffing it, that KV traffic compounds with every iteration of the loop. The loop re-pays for everything already said, every time it says something new.

What actually happens in a loop

In a single-shot completion, spend is roughly determined by the size of the input. In a loop it isn’t: the agent decides how many tokens to spend, and the outcome is undetermined before the run starts. Four scenarios show what that looks like in practice.

The clean run

Stable prefix, a handful of turns, no churn: the best case. But the structural fact underneath even the best case is that each turn re-sends the whole history, so uncached input accumulates as O(N²) in turn count. Forty turns costs roughly sixteen times what ten turns costs on the input side, not four times. Caching multiplies that curve by 0.1 but does not change its order. Most intuitions about loop cost assume linear growth.

The failed edit

An agent makes a bad change, tests fail, it reads the error and retries. The wasted tokens are not a one-time loss, sunk and forgotten: the failed attempt is now sitting in the context, and on current models so is the reasoning that produced it. Every subsequent turn re-reads that failure at input or cache-read rates, and the same quadratic accumulation applies to the failed work exactly as it does to the successful work.

THE CAPITALISATION PROBLEM

Failed work is not expensed. It is capitalised into the context and charged as rent for the remainder of the session. That’s arithmetic, not a behavioral claim: it follows directly from how the loop re-sends history on every turn.

The exploratory read

The agent greps, lists, opens files. Every tool result is input the agent chose to incur without knowing its size in advance: reading one large file can inject more tokens than the entire preceding conversation. Two runs of an identical task against differently organized repositories can differ by an order of magnitude in spend with no difference in model, prompt, or outcome.

The compaction event

The context window fills and the harness compacts it. Three things happen at once: a large summarization generation billed at output rates, cache invalidation (the next turn writes rather than reads), and lossy information loss that can cause the agent to redo work it has already done. Where the cache keys on an exact prefix, that invalidation is total rather than partial. A compaction is a step function in both cost and risk, and telemetry that only samples averages won’t see it coming until it already dominates the bill.

GO DEEPER — fan-out and the early stop

Fan-out (spawning parallel sub-agents) duplicates the prefix (each sub-agent carries its own system prompt and tool definitions), but their transcripts never enter the parent’s history; only the returned summaries do. The trade is explicit: N× duplicated prefix cost in exchange for keeping the main thread’s quadratic term small. Below some task length, fan-out is pure overhead; above it, it’s the cheaper topology. Where that crossover sits is an empirical question per harness.

The early stop cuts both ways: an agent decides for itself when it’s done, and that under-determination can either grind past the point of marginal value, or stop at 80% and hand a human the remaining 20%, usually the expensive 20%. Minimizing cost per token and minimizing cost per outcome are different objectives, and beyond a point they’re opposed.

The iceberg

WHERE THE SPEND ACTUALLY GOES

What ships (accepted output) is the visible tip. Below the waterline: reasoning tokens, intermediate context per iteration, tool-call results fed back in, discarded-and-regenerated rework, fan-out and cache-write overhead. Most of the spend is submerged.

The funnel: how work becomes yield

Getting from agent effort to token yield is a down-select, not a single measurement. Three questions, asked in order: did the agent finish the work on its own? Of what it finished, how much was actually kept? Of what was kept, how much mattered to the outcome? Each question narrows the field — and multiplying the three answers together, so strength in two dimensions can’t hide weakness in the third, is what I call the Agent Efficiency Score.

Each stage above is a question in plain language. Below are the same three stages as precise, measurable ratios — what each one counts, and the fourth, multiplicative measure they produce together.

ILLUSTRATIVE TARGETS, NOT YET VALIDATED

The numeric targets below carry over from my own earlier drafts of this framework as directional guidance, not as thresholds derived from production outcome data. What counts as a normal TER or AES in practice is still open: my own working numbers are not yet measured against production outcomes. Treat them as a starting point for instrumentation, not a pass/fail bar to report against today.

01

Autonomous Completion Rate (ACR)

ACR = completed autonomously / started

What fraction of work finished without a human bailout or escalation. Low ACR means the agent is technically "working," but a person is quietly doing the last mile on most items.

02

Token Efficiency Ratio (TER)

TER = accepted / total spend · illustrative target ≥ 0.70

What fraction of spend produced output that was kept, not reworked or discarded. Below 0.70 would indicate more than 30% of capacity going to rework (a candidate reading, not a validated one).

03

Value Generation Ratio (VGR)

VGR = value-generating / accepted

Of what you kept, how much actually mattered to the customer’s outcome. Accepted output can still be low-value: VGR catches the difference between "shipped" and "worth shipping," which is why token yield is defined against AES rather than raw acceptance (see the hub page).

04

Agent Efficiency Score (AES)

AES = TER × VGR × ACR · illustrative target ≥ 0.50

The composite is multiplied, not averaged, so it’s the site's formal name for "token yield." Below 0.35 would signal a structural problem rather than something a tuning pass fixes (again, a directional reading pending validation).

Accountability: what happens when the loop hits its limit

The safety valve and two-layer policy above (panels 02 and 03) aren’t just cost controls: they’re the mechanism the governance argument here rests on. When the monotonic cost detector fires, the loop doesn’t fail silently and it doesn’t keep going on the assumption a human will notice eventually: it stops before the next iteration would exceed budget, and hands a human reviewer the accumulated state (what’s been tried, what failed, current spend against remaining budget) rather than a bare "over budget" alert with no context to act on.

The same discipline applies to every iteration, not just the ones that trip the safety valve. Each pass through the loop produces an accept/reject decision (was that iteration’s output kept, or discarded and reworked) and that decision is what TER is counting. Recorded per iteration rather than inferred after the fact from a final diff, it becomes a literal, timestamped ledger of what was tried, what was kept, and why, not just a single aggregate ratio.

WHAT THE AUDIT TRAIL ATTRIBUTES

Because spend is metered per task through the billing and usage telemetry on the platform surfaces covered on the previous page (Copilot, Azure OpenAI, Claude on Foundry), the accept/reject ledger and the escalation record above are attributable at the task-class level, not only as one site-wide average. That's what lets an oversight review ask "which class of work has poor ACR or TER" and act on that class specifically, rather than reading a single blended number and guessing where the problem sits.

This describes the escalation and audit-trail mechanism as specified in the project's design, not a claim that any specific deployment already logs, retains, or surfaces this data in a given tool. Retention policy and dashboarding for this ledger are deployment decisions this page doesn't prescribe.
