THE AGENT LOOP

The Agent Loop

“The loop multiplies cost across repeated calls, while most of the resulting token spend remains outside the visible output.”

A single model call already carries five priced token classes, and an agentic task makes many such calls, cycling Read → Generate → Execute → Evaluate until the work passes or a limit is hit. Each repetition compounds the cost multiplicatively, and most of that multiplication never reaches the screen.

How per-call cost compounds across a loop

The loop has four steps: read the current state, generate a step, execute it and evaluate the result, repeating for as long as the work remains unfinished. Each pass is a full model call with its own five-part cost structure (input, reasoning, output, cache-write and cache-read).

THE LOOP COST MULTIPLIER

cost ≈ per-call cost × ℓ (iterations) × f (fan-out)

A one-dollar call looped 10 times costs $10, and with 3-way fan-out (parallel sub-agents) the same work item costs $30; the same multiplication applies to every item in a backlog.

01

The mechanics

Agentic systems cycle Read → Generate → Execute → Evaluate → repeat, until the work passes or a limit is hit, and each iteration is billed as a full model call.

02

The safety valve

A halt-and-escalate mechanism (a monotonic cost detector) stops the loop and escalates to a human before the next iteration would exceed the remaining budget, so the loop never continues without a check against what is left to spend.

03

Two-layer policy

Allocation policy (triage: which tier, which model, how many loops) is separate from execution policy (doing the work). Using lower-priced tokens for triage can reduce later rework on higher-priced models.

Prefill, decode and the KV cache inside a loop

The multiplier follows from the asymmetry between prefill and decode in how the accelerator does the work, the same asymmetry that prices output at around 5× input and a cache read far below a fresh input token (the Tokens page covers the prefill/decode mechanics and Foundry's cache-pricing regimes). Inside a loop, the component of that asymmetry with the largest effect on cost is the KV cache. During prefill, each layer computes a key/value vector per token so that later tokens can attend to earlier ones without recomputing them; that tensor must be read at every decode step for every token in context, with no sharing across sequences, which is why continuous batching amortizes the model’s weights but not the KV cache. Most agent harnesses re-send the entire conversation history on every turn instead of sending a diff, so KV traffic compounds with each iteration, and the loop pays again for everything already in context each time it generates something new.

Four loop scenarios

In a single-shot completion, spend is roughly determined by the size of the input; in a loop the agent decides how many tokens to spend, and the outcome is undetermined before the run starts. The four scenarios below describe the resulting cost patterns.

The clean run

The best case has a stable prefix, a handful of turns and no churn. Even then each turn re-sends the whole history, so uncached input accumulates as O(N²) in turn count: on the input side, forty turns cost roughly sixteen times what ten turns cost, where linear growth would predict four times. Caching multiplies the curve by 0.1 without changing its order, which matters because most intuitions about loop cost assume linear growth.

The failed edit

When an agent makes a bad change, the tests fail and the agent reads the error and retries. The wasted tokens keep costing money after that point, because the failed attempt stays in the context, and on current models so does the reasoning that produced it; every subsequent turn re-reads that failure at input or cache-read rates, and the same quadratic accumulation applies to the failed work as to the successful work.

COST CARRYOVER FROM FAILED WORK

In accounting terms, failed work remains capitalised in the context and incurs repeated input charges for the remainder of the session. This follows arithmetically from the loop re-sending history on every turn and depends on no assumption about agent behavior.

The exploratory read

When the agent greps, lists and opens files, each tool result is input it chose to incur without knowing the size in advance, and reading one large file can inject more tokens than the entire preceding conversation. Two runs of an identical task against differently organized repositories can differ by an order of magnitude in spend with no difference in model, prompt or outcome.

The compaction event

When the context window fills, the harness compacts it, and three things happen at once: a large summarization generation billed at output rates, cache invalidation (the next turn writes to the cache instead of reading from it), and lossy compression that can cause the agent to redo work it has already done. Where the cache keys on an exact prefix, the invalidation is total. Compaction is therefore a step function in both cost and risk, and telemetry that samples only averages will not register it until it already dominates the bill.

GO DEEPER — fan-out and the early stop

Fan-out (spawning parallel sub-agents) duplicates the prefix, since each sub-agent carries its own system prompt and tool definitions, but the sub-agents’ transcripts never enter the parent’s history; only their returned summaries do. The trade is N× duplicated prefix cost in exchange for a smaller quadratic term in the main thread. Below some task length fan-out is overhead with no offsetting saving, and above it fan-out is the cheaper topology; where the crossover sits has to be measured for each harness.

The early stop can fail in either direction, because the agent decides for itself when it has finished: it can grind past the point of marginal value, or stop at 80% and hand a human the remaining 20%, which is usually the expensive 20%. Minimizing cost per token and minimizing cost per outcome are different objectives, and beyond a point they conflict.

Visible and submerged spend

WHERE THE SPEND GOES

Accepted output is the visible portion of the work. Reasoning tokens, intermediate context per iteration, tool-call results fed back in, discarded-and-regenerated rework, and fan-out and cache-write overhead remain outside it and together account for most of the spend.

The funnel: how work becomes yield

Agent effort is converted into token yield through a down-select of three questions asked in order: whether the agent finished the work on its own, how much of what it finished was kept, and how much of what was kept mattered to the outcome. Each question narrows the field, and I call the product of the three answers the Agent Efficiency Score. Because the score is multiplicative, a low value in any one ratio reduces the composite even when the other two are high.

The panels below restate the three stages as measurable ratios, with what each one counts, followed by the fourth, multiplicative measure that combines them.

ILLUSTRATIVE TARGETS, NOT YET TESTED

The numeric targets below carry over from my earlier drafts of this framework as directional guidance and were not derived from production outcome data. What counts as a normal TER or AES in practice is still open, because my working numbers have not yet been measured against production outcomes; they are a starting point for instrumentation and should not be used as a pass/fail bar for reporting today.

01

Autonomous Completion Rate (ACR)

ACR = completed autonomously / started

The fraction of work finished without a human bailout or escalation. A low ACR means that a person completes the remaining work on most items attributed to the agent.

02

Token Efficiency Ratio (TER)

TER = accepted / total spend · illustrative target ≥ 0.70

The fraction of spend that produced kept output, meaning output that was neither reworked nor discarded. A value below 0.70 would indicate that more than 30% of capacity is going to rework; this is a candidate reading that has not been tested against outcome data.

03

Value Generation Ratio (VGR)

VGR = value-generating / accepted

The share of kept output that mattered to the customer’s outcome. Accepted output can still be low-value, and VGR measures the difference between "shipped" and "worth shipping", which is why token yield is defined against AES instead of raw acceptance (see the hub page).

04

Agent Efficiency Score (AES)

AES = TER × VGR × ACR · illustrative target ≥ 0.50

The composite is the product of the three ratios, not their average, and AES is the site's formal name for "token yield". A value below 0.35 would indicate a structural problem that a tuning pass would not fix; this too is a directional reading that has not yet been tested.

Accountability: what happens when the loop hits its limit

Besides controlling cost, the safety valve and two-layer policy above (panels 02 and 03) are the mechanism on which the governance argument here rests. When the monotonic cost detector fires, the loop neither fails silently nor continues on the assumption that a human will eventually notice; it stops before the next iteration would exceed budget and hands a human reviewer the accumulated state (what has been tried, what failed, and current spend against remaining budget), which gives the reviewer context to act on that a bare "over budget" alert would lack.

The same discipline applies to every iteration, including those that never trip the safety valve. Each pass through the loop produces an accept/reject decision (whether that iteration’s output was kept, or discarded and reworked), and TER counts those decisions. When each decision is recorded per iteration instead of being inferred afterwards from a final diff, the record becomes a timestamped ledger of what was tried, what was kept and why, in addition to the single aggregate ratio.

WHAT THE AUDIT TRAIL ATTRIBUTES

Because spend is metered per task through the billing and usage telemetry on the platform surfaces covered on the previous page (Copilot, Azure OpenAI, Claude on Foundry), the accept/reject ledger and the escalation record above can be attributed at the task-class level as well as averaged site-wide. An oversight review can therefore ask "which class of work has poor ACR or TER" and act on that class, without having to guess the location of the problem from a single blended number.

The escalation and audit-trail mechanism above is specified in the project's design; no specific deployment is claimed to log, retain or surface this data in a given tool today. Retention policy and dashboarding for the ledger are left as deployment decisions.
