Every Token Belongs to Someone

“An invoice records charges without linking them to produced outcomes, so it does not contain the data needed to compute yield.”

Managing agentic spend means attributing it while it happens: to a task, a task class and a person, with enough detail to tell a price problem from a yield problem.

Limits of the invoice as a source of yield data

For most teams the monthly bill is a reliable record of charges but a poor source for managing agentic work, because it aggregates spend by account, model and day, while yield is defined per unit of work: whether a task finished, whether its output was kept and whether it mattered. Those questions can be answered only at the level where a specific run produced a specific result, and by the time spend reaches an invoice the link back to that result has usually been lost.

The remedy therefore sits upstream of the invoice, in attaching ownership to spend at the moment it occurs, so that every token carries enough context to be traced back to the work it served.

The attribution chain

The chain runs from the smallest unit of cost to the person accountable for it: a token is consumed by a call to a model, calls make up an iteration of the loop, iterations make up a task, tasks that recur belong to a task class, and each task class has an owner. A missing link breaks the chain above it, so spend that cannot be tied to a task cannot be tied to an outcome, and spend that cannot be tied to a task class has nobody to act on it.

In practice this requires a small set of identifiers to travel with every call (a task ID, a task-class label and an owner), which is ordinary cost-allocation practice and the same tagging discipline cloud teams already apply to infrastructure. The FOCUS specification gives billing data a common shape so that tags like these are preserved from usage record to cost report. Agentic work differs in the grain it requires, since a tag per deployment is insufficient when a single deployment serves dozens of task classes whose yields differ widely.

Telemetry in tiers

Telemetry differs in how easily it can be collected, and can usefully be treated as nested tiers, each depending on the one inside it.

  1. Billing. What was charged, by account and model, which is available everywhere and sufficient for price risk only.
  2. Usage per call. Token counts by class (fresh input, cached input, output, tool results), the model tier used and the attribution tags; at this tier the token mix described on the Reframe page becomes readable.
  3. Decisions per iteration. Whether each iteration’s output was accepted or rejected, recorded when the decision is made rather than inferred later; these decisions are what TER counts.
  4. Outcomes per task. Whether the task finished without a human taking over and whether its output was used downstream. ACR and VGR come from this tier, whose data often arrives days or weeks after the spend.

Computing yield requires the outer tiers, whereas most teams currently have only billing data. Building outward one tier at a time is a reasonable sequence provided the attribution tags are in place from the start, because tags added later cannot be applied to spend that has already happened.

THE DIAGNOSTIC RULE

As a proposed heuristic, not yet tested against production data: when cost per task class spikes, look at yield for the same class over the same period. A cost spike with high yield is a price event, in which the work is still converting at a higher cost, and the places to look are rates, model routing, token mix and cache behaviour. A cost spike with low yield is a yield event, in which the loop is spending more and keeping less, and the places to look are rejection reasons, retries, stop rules and the task definition.

The rule matters because the two events have different owners and different fixes: a price event usually belongs to whoever manages the platform and its commercial terms, and a yield event belongs to the owner of the task class. A yield event sent to the platform team produces a cheaper model and a worse result, which is the failure described on the Reframe page, and a price event sent to the task-class owner produces a rewrite of work that was functioning.

In the illustrative rows, a week-on-week rise in cost per task of more than a set share, with yield flat or rising, goes to the platform owner as a price event, and the same rise with yield falling goes to the task-class owner as a yield event. A falling share of cached input suggests, on the Reframe page’s reading, that the stable prefix is churning, and goes to whoever maintains the harness. A falling completion rate, meaning more runs ending in human takeover, goes back to the task-class owner to check scope. Spend running ahead of the plan’s value milestones is the situation μ is designed to flag, and goes to the budget owner.

Claim status. None of these thresholds has been fitted to outcome data. The rule itself follows from keeping price risk and yield risk separate, and the numbers that would make it fire at the right moment are still to be measured.
